01 · Resumen Ejecutivo

¿Por qué se realizó esta intervención y qué protege hoy en Solutoday?

La revisión inicial de la línea base detectó riesgos críticos en código (sin afirmar incidentes previos en producción): rutas de mantenimiento abiertas, credenciales de terceros enviadas a los dispositivos, confianza excesiva en datos del cliente (roles, precios, estados) y falta de protección contra cobros duplicados. El Ítem 2 trasladó todas esas decisiones críticas al servidor.

LO CRÍTICO ENCONTRADO

Rutas capaces de reiniciar la base de datos, credenciales de chat e IA entregadas al cliente, registros que aceptaban roles sin control, acceso cruzado a reservas ajenas y pagos vulnerables a montos alterados o dobles débitos.

SOLUCIÓN RESPONSABLE

Se eliminaron las rutas peligrosas, se estableció control de BD por migraciones CLI, las claves quedaron en el servidor, se protegió cada operación por rol y titularidad, y los pagos corren en transacciones MySQL idempotentes.

CALIDAD VERIFICADA

Todo el paquete integrado superó 123 pruebas automatizadas y 703 aserciones sin fallos sobre MySQL aislado, además de recorridos reales en navegador Chrome y emulador Android, con evidencia por Pull Request.

05 · Gobierno y Control de Base de Datos (MySQL)

Cómo se administran y ejecutan las migraciones de la BD ahora

Tras eliminar las rutas peligrosas del instalador y el reinicio automático (PR #1), la evolución de MySQL pasa a un esquema estrictamente versionado, incremental y ejecutado únicamente por línea de comandos (CLI) bajo control operativo.

Ver diagrama de Control de BD →
Qué dejó de existir (PR #1): Se eliminaron las rutas web del instalador (/install/*), los endpoints capaces de disparar migrate:fresh / migrate:refresh y la tarea programada en Console/Kernel.php. Tampoco el contenedor (Dockerfile) ni el workflow actual ejecutan migraciones destructivas al arrancar.
Principio de operación segura: En QA y Producción jamás se ejecutan comandos destructivos (migrate:fresh / migrate:refresh). Todo cambio se aplica mediante migraciones incrementales nuevas, precedidas siempre de respaldo y simulación sin escritura (--pretend).

Protocolo de 5 pasos para aplicar migraciones en QA o Producción

Paso 1 · Respaldo
Backup previo obligatorio
Generar respaldo completo de MySQL (mysqldump) y verificar que sea restaurable antes de cualquier cambio.
Paso 2 · Diagnóstico
Consultar pendientes
Ejecutar migrate:status en modo solo lectura para confirmar exactamente qué archivos faltan por aplicar.
Paso 3 · Simulación
Revisar SQL sin escribir
Ejecutar migrate --pretend para inspeccionar el SQL exacto antes de tocar las tablas.
Paso 4 · Aplicación
Migrar solo deltas
Ejecutar migrate --force para aplicar únicamente las migraciones nuevas sin alterar datos existentes.
Paso 5 · Caché
Refrescar permisos
Ejecutar permission:cache-reset para activar inmediatamente los nuevos permisos Spatie en memoria.

Secuencia oficial por CLI (QA / Producción)

# 1. Respaldo previo obligatorio (mysqldump) antes de iniciar
# 2. Verificar migraciones pendientes (solo lectura)
php artisan migrate:status

# 3. Simular el SQL exacto sin modificar la base de datos
php artisan migrate --pretend

# 4. Aplicar únicamente las migraciones incrementales nuevas
php artisan migrate --force

# 5. Refrescar caché de permisos Spatie (postjob assign)
php artisan permission:cache-reset

Desarrollo local y nota operativa del pipeline

ENTORNO LOCAL AISLADO (LOCAL-DEV)

En desarrollo local se utiliza siempre un contenedor MySQL desechable, aplicando las migraciones de la rama y cargando únicamente datos ficticios (local-dev/fixtures/dev-data.sql). Nunca se usan volcados ni credenciales reales.

NOTA SOBRE DEPLOY-DEV.YML

El workflow actual (.github/workflows/deploy-dev.yml) construye la imagen Docker, la publica en ECR y ejecuta docker stack deploy, pero no corre migraciones automáticamente. Al autorizar un despliegue futuro, el equipo debe ejecutar el respaldo y php artisan migrate --force dentro del contenedor en esa misma ventana.

Qué necesitan incorporar clientes-v2 y proveedor-v2 para adoptar estos cambios

El Ítem 2 comprende exclusivamente Seguridad web y backend unificado (web-v2). Las actualizaciones, compilaciones y publicación en tiendas de las aplicaciones móviles no fueron cotizadas dentro de este ítem. A continuación se detalla qué requiere cada app para aprovechar las nuevas protecciones sin afectar a los usuarios actuales:
